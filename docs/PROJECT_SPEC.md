# Video Quality Analyzer — техническое задание

**Версия:** 0.1  
**Тип проекта:** локальное приложение для автоматической технической проверки видеоматериалов  
**Основной сценарий:** пользователь передаёт ссылку на видео, система скачивает материал, проверяет его по заданному профилю требований и формирует подробный отчёт.

---

# 1. Цель проекта

Разработать инструмент, который автоматически проверяет видеоматериалы на соответствие техническим требованиям заказчика.

Основная задача — исключить человеческий фактор при проверке большого количества видео.

Система должна автоматически проверять каждый критерий, не забывать отдельные пункты проверки и предоставлять измеримые результаты.

Принцип работы:

- Проверяем не субъективное впечатление от видео, а конкретные параметры.
- Каждый критерий проверяется независимо.
- Результат содержит фактическое измерение, допустимое значение и статус.
- Если критерий нельзя достоверно проверить автоматически, он получает статус REVIEW.
- Неизвестный результат никогда не считается успешным.

Проект также является практическим инструментом для демонстрации возможностей автоматизации и последующей интеграции с бизнес-процессами заказчиков.

# 2. Область первой версии (MVP)

Первая версия должна включать:

1. REST API.
2. Web-интерфейс на Angular.
3. Приём ссылок на видео.
4. Локальное скачивание видео.
5. Фоновую обработку заданий.
6. Технический анализ видеопотока.
7. Технический анализ аудиопотока.
8. Обнаружение смен сцен и склеек.
9. Настраиваемые профили требований.
10. Сохранение истории и результатов анализа.

Все операции обработки выполняются локально.

Не использовать платные внешние API и облачные LLM.

# 3. Архитектура

Основные компоненты:

## Frontend

Angular + TypeScript + Tailwind CSS.

Назначение:
- список заданий;
- создание задания;
- управление профилями требований;
- просмотр результатов;
- просмотр истории анализа;
- отображение ошибок обработки.

Frontend взаимодействует с Backend исключительно через REST API.

Обновление состояния задания на первом этапе выполняется периодическим запросом API с интервалом 5 секунд.

WebSocket, SSE и другие механизмы push-обновлений в MVP не требуются.

## Backend

Node.js + TypeScript.

Предпочтительный вариант — NestJS с REST API.

Ответственность Backend:
- управление заданиями;
- загрузка видео;
- управление очередью обработки;
- запуск анализаторов;
- хранение результатов;
- применение профилей требований;
- формирование итогового заключения.

## Database

PostgreSQL.

Хранить:
- задания;
- сведения о видео;
- профили требований;
- версии профилей;
- результаты отдельных проверок;
- итоговые заключения;
- технические ошибки.

## Media Processing

Основные инструменты:

- FFmpeg — декодирование и обработка аудио/видео.
- FFprobe — получение метаданных медиапотоков.
- PySceneDetect — обнаружение смен сцен.
- OpenCV — анализ изображения.
- Python — дополнительные алгоритмы обработки, если они удобнее или надёжнее существующих Node.js-библиотек.

Запуск внешних инструментов выполнять безопасно, без формирования shell-команд из пользовательского ввода.

# 4. Основной пользовательский сценарий

1. Пользователь открывает Web UI.
2. Выбирает профиль требований.
3. Вставляет ссылку на видео.
4. Создаёт задание.
5. Backend регистрирует задание и помещает его в очередь.
6. Система скачивает видео в локальное хранилище.
7. Запускаются необходимые анализаторы.
8. Результаты отдельных проверок сохраняются в БД.
9. После завершения проверок система применяет правила выбранного профиля.
10. Пользователь получает итоговый отчёт.

Пользователь должен иметь возможность смотреть состояние обработки, не дожидаясь её окончания.

# 5. Управление заданиями

Предусмотреть следующие статусы задания:

- QUEUED — ожидает обработки.
- DOWNLOADING — скачивание.
- ANALYZING — выполняется анализ.
- COMPLETED — анализ завершён.
- FAILED — произошла критическая ошибка.

Задание должно иметь:
- уникальный ID;
- URL источника;
- локальный путь к видео;
- ID и версию профиля;
- дату создания;
- дату начала обработки;
- дату завершения;
- текущий этап;
- процент выполнения, если его можно достоверно определить;
- описание ошибки при неудаче.

Обработка выполняется в фоне.

Не блокировать HTTP-запрос на всё время скачивания и анализа.

На первом этапе достаточно простой локальной очереди с ограничением количества параллельных заданий.

Состояние заданий должно сохраняться в PostgreSQL. После перезапуска приложения незавершённые задания не должны бесследно теряться. Предусмотреть восстановление или явную фиксацию прерванных задач.

# 6. Анализ видеопотока

Использовать FFprobe и FFmpeg.

Обязательные проверки MVP:

## 6.1. Метаданные

Получать:
- ширину и высоту кадра;
- разрешение;
- FPS;
- длительность;
- видеокодек;
- битрейт;
- соотношение сторон;
- частоту кадров (постоянная или переменная, если возможно определить);
- количество видеопотоков.

## 6.2. Целостность

Проверять:
- возможность декодирования видеопотока;
- ошибки декодирования;
- повреждённые участки;
- отсутствие видеоданных.

## 6.3. Смены сцен и склейки

Использовать PySceneDetect.

Получать:
- количество обнаруженных смен сцен;
- временные отметки;
- интервалы между сменами сцен;
- минимальный интервал;
- средний интервал.

Проверять соответствие минимальному интервалу между склейками, заданному в профиле.

Важно: детектор смен сцен не гарантирует обнаружение всех монтажных склеек. Резкое движение камеры, вспышки и другие изменения изображения могут давать ложные срабатывания. Результат должен содержать данные детектора и его настройки.

## 6.4. Изображение

Предусмотреть:
- обнаружение чёрных кадров;
- обнаружение длительных замороженных участков;
- оценку резкости;
- оценку визуального шума.

Показатели качества не должны сводиться к произвольной универсальной оценке. Сохранять исходные измерения и применять пороги профиля.

# 7. Анализ аудиопотока

Использовать FFprobe, FFmpeg и подходящие Python-библиотеки.

## 7.1. Наличие и целостность

Проверять:
- наличие аудиопотока;
- количество аудиопотоков;
- возможность декодирования;
- длительность;
- частоту дискретизации;
- количество каналов;
- аудиокодек;
- битрейт.

Наличие аудиопотока не означает, что в нём присутствует полезный звук.

## 7.2. Уровень звука

Рассчитывать:
- RMS;
- пиковый уровень;
- LUFS, если применимо;
- длительность участков тишины;
- долю тишины от общей длительности;
- признаки клиппинга.

## 7.3. Фоновый шум

Предусмотреть первоначальную оценку:
- постоянного фонового шума;
- низкочастотного гула;
- широкополосного шума;
- выраженных шумовых участков.

Не считать любой звук вне речи дефектом записи.

Пение птиц, ветер, музыка, шум окружения и технический шум микрофона — разные категории. На первом этапе можно измерять акустические характеристики, но нельзя заявлять достоверное семантическое определение всех этих событий.

Если качество записи нельзя достоверно оценить автоматически, результат должен быть REVIEW.

# 8. Синхронизация аудио и видео

Предусмотреть базовую проверку:
- временных меток потоков;
- начального смещения;
- длительности потоков;
- существенных расхождений временных шкал.

Не заявлять, что базовая проверка метаданных гарантирует синхронность речи и изображения.

Более сложное определение рассинхронизации по движению губ можно оставить для будущих версий.

# 9. Профили требований

Профили должны храниться отдельно от программного кода.

Пример параметров:

- минимальное разрешение;
- минимальный FPS;
- максимальный или минимальный допустимый битрейт;
- обязательность аудиопотока;
- минимальная громкость;
- допустимая доля тишины;
- допустимый уровень клиппинга;
- минимальный интервал между сменами сцен;
- допустимый уровень визуального шума;
- минимальная резкость.

Каждый параметр должен поддерживать:
- значение;
- единицу измерения;
- условие сравнения;
- обязательность проверки;
- включение/отключение проверки.

Профили должны иметь версии.

При создании задания фиксировать конкретную версию профиля. Изменение профиля не должно изменять уже сформированные заключения.

Возможность добавления новых критериев без изменения общей архитектуры обязательна.

# 10. Результаты проверок

Каждая проверка возвращает отдельный результат.

Статусы:

- PASS — критерий выполнен.
- FAIL — критерий не выполнен.
- REVIEW — автоматическая проверка не может дать достоверный ответ.
- ERROR — техническая ошибка выполнения проверки.
- SKIPPED — проверка отключена или не применима.

Структура результата должна содержать:

- название проверки;
- статус;
- измеренное значение;
- допустимое значение;
- единицу измерения;
- пояснение;
- временные отметки, если применимо;
- настройки алгоритма;
- версию анализатора.

Не объединять результаты разных проверок в одно неинформативное поле.

# 11. Итоговое заключение

Варианты:

- ACCEPT — все обязательные проверки пройдены.
- REJECT — хотя бы один обязательный критерий получил FAIL.
- MANUAL_REVIEW — есть обязательные проверки со статусом REVIEW или ERROR, но нет подтверждённого FAIL.

Отключённые проверки не должны автоматически считаться пройденными.

В итоговом отчёте показывать:
- общую информацию о видео;
- выбранный профиль и его версию;
- список всех проверок;
- фактические измерения;
- причины отказа;
- предупреждения;
- ошибки;
- общий результат.

# 12. REST API

Предусмотреть следующие группы endpoints.

## Задания

- POST /api/jobs — создать задание.
- GET /api/jobs — список заданий.
- GET /api/jobs/:id — состояние задания.
- GET /api/jobs/:id/report — полный отчёт.
- DELETE /api/jobs/:id — удалить задание и связанные локальные данные с учётом защиты от удаления активных задач.

## Профили

- GET /api/profiles — список профилей.
- POST /api/profiles — создать профиль.
- GET /api/profiles/:id — получить профиль.
- PUT /api/profiles/:id — обновить профиль с созданием новой версии.
- GET /api/profiles/:id/versions — история версий.

Конкретные DTO, формат ошибок и валидацию определить при проектировании API.

API должно быть независимым от конкретного интерфейса.

# 13. Безопасность и устойчивость

- Ограничить допустимые источники загрузки.
- Не допускать произвольного выполнения команд из URL.
- Использовать безопасный запуск FFmpeg и yt-dlp.
- Ограничивать размер загружаемого файла и длительность видео.
- Предусмотреть таймауты.
- Контролировать потребление памяти и параллелизм.
- Корректно обрабатывать ошибки загрузки и декодирования.
- Не удалять исходные файлы до завершения анализа.
- Предусмотреть очистку временных файлов.
- Не допускать потери истории результатов при удалении видеофайла.

# 14. Что НЕ входит в MVP

Не реализовывать сейчас:

- Telegram Bot.
- MCP Server.
- Внешние LLM API.
- Облачную обработку.
- Распознавание всех возможных объектов.
- Семантическую классификацию всех звуков.
- Автоматическую оценку соответствия тематике ролика.
- Распределённую инфраструктуру.
- Kubernetes и микросервисы.
- Сложную систему пользователей и ролей.

Архитектура должна позволять в будущем подключить Telegram, MCP и внешние системы через существующий API.

# 15. Тестирование

Обязательно подготовить набор тестовых видеоматериалов с известными характеристиками.

Минимальные тестовые случаи:
1. Корректное видео 1080p с нормальным звуком.
2. Видео с разрешением ниже допустимого.
3. Видео без аудиопотока.
4. Видео с аудиопотоком, содержащим только тишину.
5. Видео с длительными участками тишины.
6. Видео с клиппингом.
7. Видео с частыми склейками.
8. Видео с чёрными кадрами.
9. Видео с замороженным изображением.
10. Повреждённый или некорректно декодируемый файл.

Проверить, что:
- каждый критерий действительно выполняется;
- ошибки одного анализатора не блокируют остальные;
- результаты сохраняются;
- задания восстанавливаются после перезапуска;
- изменение профиля не меняет старые отчёты;
- одинаковый файл и одинаковая версия алгоритмов дают воспроизводимые измерения.

# 16. Критерии готовности MVP

MVP считается готовым, когда пользователь может:

1. Открыть Angular UI.
2. Создать профиль технических требований.
3. Передать ссылку на видео.
4. Запустить фоновый анализ.
5. Видеть состояние обработки.
6. Получить подробный отчёт.
7. Увидеть конкретные причины несоответствия.
8. Просмотреть историю предыдущих проверок.

Система не должна пропускать очевидные технические дефекты из тестового набора, в частности отсутствие аудио и полностью пустую аудиодорожку.

# 17. Принципы разработки

- Не усложнять архитектуру без реальной необходимости.
- Сначала реализовать детерминированные технические проверки.
- Не использовать ИИ там, где достаточно измерения.
- Не выдавать вероятностный результат за точный.
- Каждый анализатор должен иметь независимые тесты.
- Не дублировать бизнес-логику во Frontend.
- Не связывать анализаторы с Telegram, MCP или Angular.
- Все интеграции в будущем должны использовать REST API.
- Предпочитать простые решения, которые можно локально запустить и отладить.
