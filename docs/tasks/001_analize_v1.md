# ТЗ: Система автоматического технического анализа видео

## 1. Цель проекта

Реализовать систему автоматической проверки технического качества скачанных YouTube-видео.

Назначение системы — помогать человеку при отборе видеоматериалов для обучения нейросетей.

Пользователь самостоятельно находит видео и принимает предварительное решение о его пригодности. Система выполняет техническую проверку и показывает потенциальные проблемы, которые человек мог пропустить при просмотре.

Система НЕ должна заменять человека при оценке содержимого видео.

Основной принцип: автоматизировать объективно измеримые характеристики и указывать проблемные участки с таймкодами.

## 2. Текущий стек

Использовать существующие технологии проекта:

- NestJS
- TypeScript
- PostgreSQL
- Drizzle ORM
- BullMQ
- FFmpeg / FFprobe
- yt-dlp (существующая загрузка видео)

Не добавлять альтернативные механизмы очередей, ORM или отдельные серверы.

Перед началом работы изучить существующую структуру проекта, модели БД, механизм загрузки видео и очередь задач.

Не создавать дублирующие сущности и сервисы.

## 3. Общая схема работы

1. Пользователь скачивает видео с YouTube существующим механизмом.
2. Пользователь запускает технический анализ.
3. Создаётся запись анализа в PostgreSQL.
4. Задача помещается в существующую очередь BullMQ.
5. Фоновый Worker выполняет проверки.
6. Результаты каждой проверки сохраняются в PostgreSQL.
7. После завершения пользователь может получить полный отчёт.

Анализ должен выполняться в фоне. HTTP-запрос не должен ждать окончания обработки видео.

## 4. Профили требований

Критерии проверки не должны быть жёстко зашиты в программный код.

Создать механизм профилей требований (AcceptanceProfile).

Профиль содержит:

- id
- name
- description
- version
- isActive
- createdAt
- updatedAt

Каждый профиль содержит набор включённых проверок с параметрами.

Параметры критериев хранить в JSONB либо в соответствии с уже принятой структурой проекта.

При запуске анализа сохранять снимок профиля и его версию. Последующее изменение требований не должно менять результаты предыдущих анализов.

Предусмотреть возможность в дальнейшем создавать несколько профилей с разными требованиями.

## 5. Проверки видео

### 5.1. Разрешение

Проверять фактические характеристики видеопотока через FFprobe.

Параметры:
- минимальная ширина;
- минимальная высота;
- соотношение сторон;
- длительность;
- битрейт видеопотока.

Базовое требование: Full HD 1920×1080.

Важно: наличие разрешения 1920×1080 в метаданных не доказывает, что видео действительно имеет детализацию Full HD.

Предусмотреть отдельную экспериментальную проверку признаков искусственного увеличения разрешения (upscaling).

Результаты:
- фактическое разрешение;
- соответствие минимальным требованиям;
- подозрение на upscaling;
- измеренные показатели.

Нельзя объявлять upscaling доказанным только на основании низкой резкости.

### 5.2. Наличие звука

Проверить наличие аудиопотока через FFprobe.

Проверить, содержит ли аудиопоток фактический сигнал.

Обнаруживать:
- отсутствие аудиодорожки;
- полностью пустую дорожку;
- длительные участки абсолютной тишины.

Отсутствие аудиодорожки при обязательном звуке — FAIL.

### 5.3. Частые склейки

Реализовать обнаружение смен сцен с использованием подходящей библиотеки или OpenCV.

Основной критерий: частота склеек.

Настраиваемые параметры:
- минимальный допустимый интервал между склейками;
- допустимое количество частых склеек;
- чувствительность обнаружения смен сцен.

Базовое значение минимального интервала: 5 секунд.

Сохранять:
- общее количество склеек;
- таймкоды;
- интервалы между соседними склейками;
- количество интервалов меньше допустимого;
- самые короткие интервалы.

Результат должен позволять человеку быстро перейти к проблемным участкам видео.

### 5.4. Анализ фонового шума

Предусмотреть отдельный анализатор аудио.

Цель — выявлять технически плохую запись, в частности:
- постоянный фоновый шум;
- ветер и низкочастотные помехи;
- шум, мешающий восприятию речи;
- перегрузку микрофона.

Предусмотреть возможность использовать:
- RMS;
- LUFS;
- спектральные характеристики;
- оценку SNR;
- VAD для обнаружения речи.

Важно: само наличие фонового шума не всегда означает брак.

Необходимо отличать отсутствие речи от ситуации, когда речь присутствует, но её перекрывает шум.

Если достоверная оценка невозможна, возвращать WARNING и измеренные показатели, а не придумывать FAIL.

Пороговые значения должны настраиваться в профиле требований.

### 5.5. Визуальные проверки

Предусмотреть расширение системы следующими проверками:

- пересветы;
- слишком тёмные кадры;
- размытость;
- длительные чёрные экраны;
- замороженные кадры;
- выраженные артефакты сжатия.

На первом этапе не требуется реализовывать сложное обнаружение артефактов сжатия.

Для каждой проверки предусмотреть возможность включения, отключения и настройки порогов.

## 6. Архитектура анализаторов

Каждая проверка должна быть отдельным независимым анализатором.

Предусмотреть общий интерфейс анализатора.

Анализатор получает:
- информацию о видео;
- путь к локальному файлу;
- параметры критерия.

Возвращает стандартизированный результат:
- тип проверки;
- статус;
- измеренные значения;
- ожидаемые значения;
- описание результата;
- проблемные таймкоды;
- дополнительные метрики.

Ошибка одного анализатора не должна останавливать остальные проверки.

## 7. Хранение результатов

Предусмотреть сущности:

### AnalysisRun

Один запуск анализа конкретного видео.

Содержит:
- videoId;
- profileId;
- profileVersion;
- profileSnapshot;
- status;
- startedAt;
- completedAt;
- error.

Статусы:
QUEUED, RUNNING, COMPLETED, FAILED.

### AnalysisCheckResult

Результат отдельной проверки.

Содержит:
- analysisRunId;
- checkType;
- status;
- measuredValue;
- expectedValue;
- details;
- createdAt.

Статусы:
PASS, FAIL, WARNING, ERROR, SKIPPED.

### AnalysisEvidence

Проблемные участки видео.

Содержит:
- analysisCheckResultId;
- timestamp;
- problemType;
- measuredValue;
- details.

Формат хранения дополнительных метрик может быть JSONB.

## 8. API

Предусмотреть API:

- получение списка профилей;
- создание профиля;
- изменение профиля;
- получение профиля;
- запуск анализа видео;
- получение списка анализов;
- получение статуса анализа;
- получение полного отчёта.

Предусмотреть описания типов для swagger, чтобы генерировать модели для фронтенд

Не создавать отдельный frontend в рамках этой задачи.

## 9. Надёжность

- Не запускать одновременно несколько одинаковых анализов одного видео и профиля без явного запроса пользователя.
- Корректно обрабатывать повторные попытки BullMQ.
- Не терять уже сохранённые результаты при ошибке отдельной проверки.
- Сохранять ошибки отдельных анализаторов.
- Не запускать анализ, если локальный файл отсутствует.
- Не удалять исходные видео после анализа.
- Не допускать бесконтрольного параллельного запуска тяжёлых задач.

## 10. Этапы реализации

Работать последовательно.

### Этап 1. Инфраструктура и базовые проверки

Реализовать:
- профили требований;
- хранение запусков и результатов;
- фоновую очередь;
- общий интерфейс анализаторов;
- проверку разрешения через FFprobe;
- проверку наличия аудио;
- обнаружение тишины;
- обнаружение частых склеек.

После этого этапа система должна полностью проходить путь от запуска анализа до сохранения результатов.

### Этап 2. Анализ звука

Добавить:
- измерение громкости;
- обнаружение clipping;
- анализ фонового шума;
- оценку SNR;
- обнаружение речи при помощи VAD.

Проверить работу на реальных видеороликах.

### Этап 3. Анализ изображения

Добавить:
- пересветы;
- тёмные кадры;
- размытость;
- чёрные экраны;
- замороженные кадры;
- экспериментальное обнаружение upscaling.

### Этап 4. Расширенные проверки

Экспериментально исследовать обнаружение артефактов сжатия и возможность объективной оценки визуальной детализации.

Не включать ненадёжные алгоритмы в обязательную приёмку без проверки на реальных материалах.

## 11. Ограничения разработки

- Не переписывать существующую систему загрузки YouTube.
- Не удалять существующие таблицы, данные и модули.
- Не пересоздавать PostgreSQL и Docker volumes.
- Все изменения схемы БД выполнять через Drizzle migrations.
- Не добавлять LLM в технические проверки.
- Не добавлять Telegram, MCP и внешние интеграции.
- Не создавать сложную универсальную систему плагинов.
- Не реализовывать гипотетические функции, отсутствующие в требованиях.

Перед изменением файлов изучить существующую реализацию и использовать её возможности.

## 12. Критерии приёмки первого этапа

1. Можно создать профиль требований.
2. Можно изменить пороги проверок.
3. Можно запустить анализ ранее скачанного видео.
4. Задача выполняется в фоне.
5. Можно проверить фактическое разрешение видео.
6. Обнаруживается отсутствие аудиопотока.
7. Обнаруживаются участки тишины.
8. Определяются склейки и интервалы между ними.
9. Результаты сохраняются в PostgreSQL.
10. Можно получить полный отчёт через API.
11. Ошибка отдельной проверки не прерывает остальные проверки.
12. Изменение профиля не меняет результаты предыдущих анализов.

## 13. Формат работы Codex

Сначала изучить текущую реализацию и определить, какие существующие модули можно использовать.

Не переписывать существующие файлы целиком без необходимости.

Реализовывать поэтапно, не пытаться выполнить все четыре этапа за один проход.

После каждого этапа:
- проверить TypeScript;
- проверить сборку;
- проверить миграции;
- проверить работу на реальном скачанном видео;
- перечислить созданные и изменённые файлы;
- указать выполненные критерии и оставшиеся проблемы.

Если обнаружено противоречие между ТЗ и существующим кодом, сначала сообщить о нём, не ломая работающую функциональность.
