# Авторизация, роли и управление пользователями

Изучи существующую архитектуру Video Quality Analyzer, API, Angular frontend, модели пользователей и заданий, созданные в задаче 004.

Реализуй минимальную, но рабочую систему авторизации и управления пользователями.

## 1. Роли

Добавить пользователям роль:

- `admin` — полный доступ к пользователям, заданиям и анализам.
- `user` — доступ только к собственным заданиям и анализам.

Использовать простую строковую роль. Не создавать отдельную систему permissions/RBAC.

## Первоначальный администратор

При первом запуске приложения, если в БД ещё нет пользователей, автоматически создать администратора:

- Логин: `admin`
- Пароль: `admin`
- Роль: `admin`
- `must_change_password = true`

Требования:

1. Пароль хранить только в виде хеша.
2. Создавать администратора только при первоначальной инициализации пустой таблицы пользователей. Не пересоздавать его при последующих запусках.
3. При первом входе требовать сменить пароль перед доступом к остальному приложению.
4. Добавить в Angular раздел «Мой профиль» со сменой собственного пароля.
5. После успешной смены пароля сбрасывать `must_change_password`.
6. Администратор должен иметь возможность сбрасывать пароли других пользователей с требованием смены при следующем входе.
7. Не допускать повторного создания стандартного администратора после его удаления или переименования.

Не реализовывать CLI-команду или отдельный seed для ручного создания первого администратора.

## 2. Авторизация Web

- Реализовать вход по логину и паролю.
- Хранить пароли только в виде безопасных хешей.
- Использовать серверные сессии с HttpOnly cookie.
- Реализовать logout и endpoint получения текущего пользователя (`/me` или аналогичный).
- Не реализовывать самостоятельную регистрацию, восстановление пароля, OAuth или подтверждение email.
- Не выводить секреты и пароли в логи.

## 3. Авторизация API

- Защитить API заданий, анализов и результатов.
- Для обычного пользователя разрешить операции только над собственными данными.
- Администратору разрешить работу со всеми данными.
- При создании задания определять `created_by_user_id` из авторизованной сессии, а не из произвольного тела запроса.
- При запуске анализа определять `requested_by_user_id` из текущего пользователя.
- Проверять права на сервере при чтении списков, получении деталей, запуске анализа и скачивании результатов.
- Использовать корректные HTTP-коды 401 и 403.
- Не ломать внутренние вызовы очередей и фоновых обработчиков.

## 4. Подготовка для Telegram и MCP

Предусмотреть возможность последующего подключения сервисных клиентов через API-ключи.

Не реализовывать Telegram-бота и MCP в этой задаче.

Если сервисная авторизация необходима для текущей архитектуры, реализовать минимальный механизм без универсальной системы токенов и разрешений.

## 5. Управление пользователями — Backend

Реализовать административные операции:

- Получить список пользователей.
- Создать пользователя с логином, паролем и ролью.
- Изменить отображаемое имя и роль.
- Активировать или деактивировать пользователя.
- Сбросить пароль пользователя администратором.

Не разрешать удаление пользователя, если это нарушит целостность истории заданий.

Запретить деактивацию или понижение роли последнего активного администратора.

## 6. Angular frontend## 6. Angular frontend

Реализовать:

### Авторизация
- Страницу входа по логину и паролю.
- Восстановление состояния авторизации через `/me` при загрузке приложения.
- Route guards для защищённых страниц.
- Централизованную обработку HTTP 401 через interceptor.
- При истечении сессии очищать состояние авторизации и перенаправлять пользователя на страницу входа.
- После повторного входа по возможности возвращать пользователя на ранее открытую страницу.
- HTTP 403 обрабатывать отдельно: показывать сообщение об отсутствии доступа, не выполнять logout.
- Реализовать выход из системы с завершением серверной сессии.

### Навигация
Добавить общее меню приложения:

- **Видео** — существующий список видео и анализов.
- **Пользователи** — управление пользователями, только для роли `admin`.
- **Профиль** — просмотр собственных данных и смена пароля.
- **Выход** — завершение сессии.

Меню должно отображаться на всех защищённых страницах, но не на странице входа.

Активный раздел должен быть визуально выделен.

### Управление пользователями
- Список пользователей с логином, именем, ролью и статусом.
- Создание и редактирование пользователя.
- Активация и деактивация.
- Сброс пароля администратором.
- Запрет доступа обычных пользователей к разделу, включая прямой переход по URL.

### Профиль
- Отображать логин, имя и роль текущего пользователя.
- Разрешить смену собственного пароля с проверкой текущего.
- При `must_change_password = true` направлять пользователя на обязательную смену пароля до доступа к остальным разделам.

### UI
Использовать существующий Angular-стек и стиль проекта. Не подключать новый UI-фреймворк без необходимости. Обеспечить нормальное отображение на десктопе и мобильном экране.

Не изменять существующий функционал анализа видео сверх необходимой интеграции с авторизацией.

## 7. Доступ к заданиям и анализам

- Обычный пользователь видит только собственные задания и анализы.
- Администратор видит все.
- Обычный пользователь может запускать анализ только для собственных видео/заданий.
- Не допускать обхода проверок через прямые запросы по ID.
- Для исторических записей без владельца предусмотреть доступ администратору.

## 8. Совместимость и миграции

- Использовать существующую таблицу `users` из задачи 004.
- Добавить необходимые поля и индексы миграциями.
- Сохранить существующие данные.
- Не менять аналитическое ядро, FFmpeg, очереди и профили качества.
- Обновить `.env.example` и README.
- Не добавлять Docker-сервисы без необходимости.
